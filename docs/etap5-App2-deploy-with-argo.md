# Deploying the Second Application (demo2.local) with ArgoCD, Ingress and TLS

This document describes the deployment of the second demo application (`demo-app-2`) using GitOps with ArgoCD.  
The application is exposed through NGINX Ingress with TLS certificates issued by cert-manager.  
Traffic from Windows is routed through NodePort due to WSL2 networking limitations.

---

## 1. Application Structure

The second application is stored under:
k8s/apps/demo-app-2/

Files included:

- `deployment.yaml`
- `service.yaml`
- `ingress.yaml`
- `certificate.yaml`

Each file defines a separate Kubernetes resource required for the application.

---

## 2. ArgoCD Application Definition

The GitOps configuration for the second application is located at:
k8s/argocd/demo-app-2.yaml

ArgoCD uses this manifest to:

- create the namespace `demo-app-2`
- apply all resources from `k8s/apps/demo-app-2/`
- keep the application synchronized with the Git repository

ArgoCD status after deployment:

- **Healthy**
- **Synced**

---

## 3. Ingress Configuration (demo2.local)

The application is exposed via NGINX Ingress using the hostname:
demo2.local

Ingress routes traffic to the `demo-app-2` service on port 80.

TLS is enabled using a certificate generated by cert-manager.

---

## 4. TLS Certificate

The certificate is defined in:
k8s/apps/demo-app-2/certificate.yaml

Certificate details:

- Issuer: `selfsigned` (ClusterIssuer)
- Secret: `demo-app-2-tls`
- DNS name: `demo2.local`

Certificate status:
READY = True

This confirms that cert-manager successfully issued the TLS certificate.

---

## 5. NodePort Exposure (WSL2 Networking)

WSL2 does not support LoadBalancer or host networking.  
Therefore, HTTPS traffic is exposed through NodePort:
HTTPS → 30259
HTTP  → 31745

Both demo applications share the same NodePort because routing is based on hostname, not port.

---

## 6. Windows Hosts Configuration

To allow Windows to resolve the hostname, the following entry was added:
172.24.64.69 demo2.local

This maps the hostname to the WSL2 virtual network interface.

---

## 7. Accessing the Application

Open in Windows browser:
https://demo2.local:30259


Expected result:

- NGINX welcome page
- Valid TLS certificate (self-signed)
- Application reachable through Ingress

---

## 8. Summary

- Second application deployed via ArgoCD  
- Independent namespace, ingress, certificate, and TLS secret  
- Routing based on hostname (`demo2.local`)  
- HTTPS access from Windows works correctly  
- Application is **Healthy** and **Synced** in ArgoCD  

This completes the deployment of the second application in Stage 2.
